# Анализ текущей интеграционной архитектуры «Здоровье+»

На основе предоставленных данных (выгрузка из Jira, тикеты Service Desk, отзывы сотрудников) составлен список выявленных системных проблем, рисков и их потенциального влияния на запуск и стабильность мобильного приложения.

| Проблема | Признаки | Влияние на приложение |
| :--- | :--- | :--- |
| **1. Отсутствие идемпотентности и надежности в Платёжном шлюзе** | **Jira:** INT-001 (при тайм-ауте деньги списываются, статус не фиксируется).<br>**Service Desk:** SD-002 (ошибка «Booking not found» после оплаты), SD-009 (двойное списание).<br>**Отзывы:** Марина (менеджер по развитию) жалуется на двойные списания и падение платежей; SD-004 (приложение виснет при оплате). | Пользователи будут массово сталкиваться с зависаниями при оплате. В случае тайм-аута (что часто бывает на мобильных сетях) деньги будут списываться, а запись не создаваться. Это приведет к негативу, возвратам и оттоку пользователей. |
| **2. Отсутствие идемпотентности в сервисе Расписания** | **Jira:** INT-005 (дубли записей при повторных POST-запросах).<br>**Service Desk:** SD-003 (дубль записи при двойном нажатии).<br>**Отзывы:** Дмитрий (техлид расписания) подтверждает отсутствие идемпотентности; Олег (руководитель контакт-центра) жалуется на двойные записи. | Мобильное приложение склонно к повторной отправке запросов при плохом интернете или случайном двойном нажатии. Пользователи будут создавать дубли записей, что вызовет путаницу в расписании врачей и необходимость ручной отмены через кол-центр. |
| **3. Нестабильность legacy-системы 1С (Проверка полисов) и отсутствие Rate Limiting** | **Jira:** INT-003 (ошибка 503 на пиках >50 rps).<br>**Service Desk:** SD-001 (зависает >30 сек, помогает только перезагрузка), SD-008 (возвращает null, через 5 минут работает).<br>**Отзывы:** Анна (Product Owner) и Алексей (разработчик интеграций) подтверждают нестабильность 1С и отсутствие лимитов. | Мобильное приложение не сможет обеспечить сценарий записи по ДМС. При пиковых нагрузках (вечером, когда люди дома пользуются приложением) 1С упадет, и приложение будет выдавать ошибки «Полис недействителен» или тайм-ауты. |
| **4. Ненадежная интеграция LIS -> CRM (FTP и устаревший REST API)** | **Jira:** INT-002 (FTP падает с ошибкой 425, задержка до 2 часов), INT-008 (дубли XML), INT-011 (неактуальные анализы в CRM).<br>**Service Desk:** SD-005 (утром нет анализов, скрипт упал ночью).<br>**Отзывы:** Елена (DevOps) и Алексей (разработчик интеграций) указывают на отсутствие автоматических повторов (retry) и хрупкость Perl-коннектора. | Главная цель приложения — «получение результатов анализов без звонка». Из-за ненадежной интеграции результаты будут либо задерживаться на часы/дни, либо приходить в CRM с дублями (что приведет к отображению мусора в приложении). |
| **5. Перегрузка очередей RabbitMQ (Сервис уведомлений)** | **Jira:** INT-004 (нет документации по лимитам).<br>**Service Desk:** SD-006 (очередь переполнена, пуш не пришел).<br>**Отзывы:** Елена (DevOps) подтверждает, что RabbitMQ работает «на честном слове» и падает при пиках. | Без пуш-уведомлений (о готовности анализов, подтверждении записи) ценность мобильного приложения падает в разы. Пользователи не будут узнавать о статусах, что увеличит нагрузку на кол-центр. |
| **6. Отсутствие распределенного трейсинга (Distributed Tracing)** | **Jira:** INT-007 (сложно найти корень сбоя).<br>**Косвенно:** Огромное количество проблем со сквозными сценариями (SD-002, SD-008). | Без сквозной трассировки (например, через OpenTelemetry) разработчики мобильного приложения не смогут понять, на каком этапе (приложение -> API GW -> 1С -> Расписание) произошла ошибка. Это критически замедлит вывод исправлений и поддержку MVP. |
| **7. Уязвимости безопасности и проблемы с сессиями** | **Jira:** INT-006 (SQL-инъекция в поиске).<br>**Service Desk:** SD-007 (врач видит чужого пациента — подмена сессии). | Высокий риск утечки персональных данных (ПДн) и медицинской тайны при выводе мобильного приложения в публичное поле. Подмена сессии в мобильном приложении может привести к тому, что пациент увидит чужие анализы. |
| **8. Отсутствие API Gateway для мобильного трафика** | **Jira:** INT-010 (Epic: разработать API Gateway с rate limiting и идемпотентностью).<br>**Отзывы:** Анна (Product Owner) говорит, что MVP буксует; Алексей упоминает отсутствие лимитов (Rate Limiting) на 1С. | Прямые запросы из мобильного приложения к legacy-системам (1С, Расписание) положат их при первых же пиковых нагрузках. Приложению нужен единый шлюз для кеширования, ретраев и защиты бэкенда (цель — 500 и 50 000 пользователей). |
