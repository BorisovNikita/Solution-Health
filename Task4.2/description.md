# Стратегия горизонтального масштабирования

| ИТ-система | Реализация горизонтального масштабирования | Ограничение выбранного метода | Описание решения для ограничения |
| :--- | :--- | :--- | :--- |
| **1С («Полисы»)** | **Кластеризация серверов 1С + Кэширование на уровне API.** Развертывание кластера серверов 1С (несколько рабочих процессов) для распределения запросов. Внедрение Redis для кэширования результатов проверки полисов (TTL 15-30 минут) перед вызовом 1С. | **Лицензирование и блокировки на уровне СУБД.** 1С — legacy-монолит. При добавлении новых серверов 1С нагрузка перекладывается на общую базу данных (MS SQL/PostgreSQL), которая начинает блокировать потоки. Кроме того, лицензии на серверы 1С стоят дорого. | **Выделение чтения (Read Replicas) или вынос логики.** Настроить репликацию базы данных 1С для операций только на чтение (проверка полиса). |
| **Расписание (Сервис + PostgreSQL)** | **Горизонтальное масштабирование приложения (Java) + Репликация БД.** Масштабирование самих Java-сервисов (Stateless) через Kubernetes (HPA) при росте CPU. Для базы данных — создание архитектуры Primary-Replica (один мастер для записи, несколько реплик для чтения). | **Задержка репликации (Replication Lag).** При записи новой записи (бронировании слота) в Master-базу, данные не мгновенно попадают в Read-реплики. Если пациент сразу обновит экран, он может не увидеть свою запись или увидеть слот занятым. | **Маршрутизация.** На уровне BFF или приложения гарантировать, что в течение N секунд (например, 2-3 секунды) после операции записи все запросы чтения от этого конкретного пользователя идут на Master-ноду. Также можно использовать синхронную репликацию для критически важных транзакций. |
