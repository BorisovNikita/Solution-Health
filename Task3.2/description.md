**Выбранный тип SAGA: Оркестрация (Orchestration).**

Выбор паттерна «Оркестрация» обусловлен жесткой последовательностью шагов и необходимостью централизованного управления компенсирующими транзакциями (откатами) при сбоях. В сценарии участвуют несколько разнородных систем (включая legacy-системы 1С и LIS) и внешний платежный шлюз, поэтому наличие единого оркестратора позволяет четко отслеживать состояние всей транзакции. В случае сбоя на любом из этапов (например, при оплате) оркестратор гарантированно инициирует откат уже выполненных шагов (отмену брони слота и резервирования в LIS), что невозможно эффективно контролировать при использовании хореографии.

---

**Таблица компенсирующих транзакций**

| Шаг сценария | Компенсирующее действие | Риск, который устраняется |
| :--- | :--- | :--- |
| **1. Бронирование слота врача в Расписании** | Отмена брони слота (`Cancel Booking` по ID брони) | «Мертвые» слоты. Пациент не оплатил услугу, но время врача заблокировано, и другие пациенты не могут записаться. |
| **2. Списание денежных средств в Платёжном шлюзе** | Возврат средств (`Refund` по ID транзакции) | Двойное списание или списание без оказания услуги. Если лаборатория не может зарезервировать время, пациент не должен терять деньги. |
| **3. Резервирование времени в LIS (Лаборатория)** | Отмена резервирования (`Cancel Reservation` по ID) | Перегрузка лаборатории и двойное бронирование времени забора биоматериалов, если последующие шаги завершатся ошибкой. |

---

**Механизм: Idempotency Key на уровне API Gateway.**

1.  **Генерация ключа:** Мобильное приложение при попытке создать запись генерирует уникальный ключ (UUID) и передает его в HTTP-заголовке `Idempotency-Key`.
2.  **Проверка на шлюзе:** API Gateway перехватывает запрос и проверяет наличие этого ключа в быстром хранилище (например, Redis).
    *   *Если ключа нет:* Шлюз сохраняет ключ со статусом `IN_PROGRESS` и передает запрос в Saga Orchestrator.
    *   *Если ключ есть, и статус `SUCCESS`:* Шлюз просто возвращает пациенту сохраненный результат предыдущего успешного запроса, не создавая новую SAGA и не списывая деньги.
    *   *Если ключ есть, и статус `IN_PROGRESS`:* Шлюз возвращает ошибку `409 Conflict` (запрос уже обрабатывается).
3.  **Результат:** Даже если у пациента «завис» интернет, и приложение отправило 3 одинаковых запроса подряд, в системе создастся только одна запись, спишутся деньги только один раз, а слот в лаборатории забронируется единожды.
